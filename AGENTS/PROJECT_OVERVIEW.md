# PROJECT_OVERVIEW.md

# Trust404 Track 3 — Verifiable Off-chain Decision Layer for Agent Payments

## 0. 이 문서의 목적

이 문서는 Codex가 프로젝트를 처음 열었을 때 **“우리가 무엇을 왜 만들고 있는지”**를 빠르게 이해하기 위한 전체 프로젝트 개요 문서다.

이 문서에는 제품의 목적, 문제 정의, 핵심 사용자 흐름, MVP 범위, 대표 데모 시나리오만 담는다.

구현 세부사항, API, 데이터 스키마, 서명 방식, Anchor Contract, 테스트 구조 등은 추후 `DEVELOPMENT.md`에서 별도로 정의한다.  
화면 구조와 UX/UI는 추후 `DESIGN.md`에서 별도로 정의한다.

---

## 1. 프로젝트 한 줄 정의

**Agent와 기관 사이에서 발생한 오프체인 결제 승인·거절 판단의 증거를 남기고, 분쟁 발생 시 어느 한쪽의 내부 DB도 신뢰하지 않고 제3자가 사실관계를 독립적으로 검증할 수 있게 하는 Verification Layer**

---

## 2. 우리가 해결하려는 문제

Agent Payment가 확대되면 AI Agent가 사용자를 대신해 결제를 요청하고, 기관 Wallet이나 결제 인프라가 기업 정책에 따라 해당 요청을 승인하거나 거절하는 상황이 늘어날 수 있다.

이때 실제 결제가 실행되지 않은 **거절·보류 같은 오프체인 판단**은 온체인 트랜잭션으로 자연스럽게 남지 않고 기관 내부 DB나 로그에만 남을 수 있다.

문제는 이후 분쟁이 발생했을 때다.

예를 들어:

- Agent는 “나는 실제로 이 요청을 보냈다”고 주장할 수 있다.
- 기관은 “그 요청을 받은 적이 없다”고 주장할 수 있다.
- 기관은 “당시 정책상 거절이 맞았다”고 주장할 수 있다.
- 과거 기록이 수정되거나 삭제되었을 수 있다.
- 어느 한쪽의 내부 DB만 보고는 제3자가 사실관계를 독립적으로 확인하기 어렵다.

현재 우리가 상정한 형태의 실제 분쟁 사례가 이미 다수 공개된 것은 아니다.

다만 Agent Payment 표준과 결제 인프라가 이미 분쟁 증거, 권한 증명, Receipt 구조를 별도로 다루기 시작했다는 점에서 **Agent가 실제 결제 권한을 행사하기 전에 검증 가능한 증거 구조를 준비할 필요가 있다**고 본다.

우리 프로젝트는 이 문제를 사전에 검증하는 프로토타입이다.

---

## 3. 우리가 만드는 것

우리는 새로운 Agent Payment 프로토콜 전체를 만들지 않는다.

기관 Wallet을 새로 만드는 것도 아니고, 결제 정책 엔진을 만드는 것도 아니다.

우리가 만드는 것은 다음 두 역할을 가진 **독립 Verification Layer**다.

### 평상시 — Evidence Capture

Agent의 결제 요청과 기관의 승인·거절 판단이 발생하는 순간, 이후 검증에 필요한 최소한의 증거를 기관 내부 시스템과 분리된 형태로 남긴다.

### 분쟁 시 — Independent Verification

제3자는 Agent나 기관의 내부 DB를 직접 신뢰하지 않고, 당시 남겨진 증거를 이용해 다음 사실을 확인한다.

- 실제 요청이 존재했는가
- 누가 요청했는가
- 어떤 정책이 적용됐는가
- 어떤 결정이 내려졌는가
- 결정이 정책과 일치하는가
- 기록이 이후 수정·삭제·누락되지 않았는가

핵심은 **“기관의 현재 로그를 믿는 것”이 아니라 “당시 남겨진 증거를 다시 검증하는 것”**이다.

---

## 4. MVP에서 다루는 정확한 상황

Agent Payment 전체를 다루지 않고 다음 상황 하나로 좁힌다.

> **기업의 AI Agent가 디지털자산 결제를 요청하고, 기관 Wallet이 실제 결제를 실행하기 전에 기업의 사전 정책에 따라 승인 또는 거절하는 상황**

### 기준 데모

기업 정책:

> 1회 결제 한도: **$4,000 USDC**

Agent 요청:

> **$4,500 USDC 결제 요청**

기관 판단:

> **REJECT — LIMIT_EXCEEDED**

이 한 건의 거절을 기준으로 전체 제품 흐름과 검증 구조를 구현한다.

---

## 5. 핵심 참여자

### Enterprise

Agent가 따라야 할 결제 정책을 사전에 정의하는 기업.

MVP에서는 단 하나의 정책만 사용한다.

> “1회 결제 금액은 최대 $4,000 USDC”

### Agent

기업을 대신해 결제 요청을 생성하는 AI Agent.

Agent가 실제로 어떤 요청을 만들었는지 이후 부인할 수 없도록 요청 자체에 대한 증거가 필요하다.

### Verification Layer

Agent와 기관 사이에서 요청과 판단의 증거를 독립적으로 기록하는 본 프로젝트의 핵심 레이어.

기관보다 먼저 Agent 요청을 관측하고, 이후 기관의 결정까지 하나의 검증 가능한 흐름으로 연결한다.

### Institution Wallet

기업 정책을 확인한 뒤 실제 결제를 승인하거나 거절하는 기관 측 Wallet 또는 결제 인프라.

### Third-party Verifier

분쟁이 발생했을 때 Agent나 기관 어느 한쪽도 신뢰하지 않고 증거를 확인하는 제3자.

예: 기업 감사 담당자, 분쟁 조정자, 외부 감사인 등.

---

## 6. 제품의 핵심 흐름

전체 흐름은 다음과 같다.

**1. Enterprise가 정책을 미리 설정한다.**

> 최대 $4,000 USDC

↓

**2. Agent가 $4,500 USDC 결제를 요청한다.**

↓

**3. Verification Layer가 요청을 먼저 관측하고 증거를 남긴다.**

↓

**4. 요청을 Institution Wallet으로 전달한다.**

↓

**5. Institution Wallet이 정책을 확인한다.**

> $4,500 > $4,000

↓

**6. 기관이 요청을 거절한다.**

> REJECT — LIMIT_EXCEEDED

↓

**7. Verification Layer가 해당 결정의 증거도 남긴다.**

↓

**8. 이후 분쟁이 발생하면 Third-party Verifier가 당시 요청·정책·결정을 다시 검증한다.**

---

## 7. Verification Layer가 요청 경로에 있어야 하는 이유

기관이 요청을 받은 뒤 스스로 접수증을 남기는 구조만으로는 부족하다.

기관이 불리한 요청에 대해 애초에 접수 기록을 만들지 않는다면, 나중에 요청의 존재 자체를 독립적으로 확인하기 어렵기 때문이다.

따라서 MVP에서는 다음 흐름을 기본 전제로 한다.

> **Agent → Verification Layer → Institution Wallet**

Verification Layer가 기관보다 먼저 요청을 관측해야 다음 상황을 구분할 수 있다.

- 요청 존재 + 결정 존재 → 정상
- 요청 존재 + 아직 결정 기한 전 → 처리 중
- 요청 존재 + 결정 기한 초과 + 결정 없음 → 결정 기록 누락
- Verification Layer에 원 요청 자체가 없음 → 검증 가능한 공식 요청으로 인정하지 않음

이 구조가 누락 탐지와 독립 검증의 출발점이다.

---

## 8. 정책은 어디까지 검증하는가

MVP에서는 정책 엔진 전체를 만들지 않는다.

정책은 다음 한 줄로 고정한다.

> **요청 금액 ≤ 기업이 정한 1회 결제 한도**

따라서 Verifier가 확인해야 하는 것은 단순하다.

예:

- 요청 금액: $4,500
- 당시 한도: $4,000
- 기관 결정: REJECT

→ 해당 거절은 당시 정책과 일치한다.

정책 자체의 복잡한 변경 이력, KYT 점수, AI 위험 판단, AML 판단 정확도 등은 MVP 범위에서 제외한다.

---

## 9. 우리가 검증하려는 네 가지

Trust404 Track 3의 목적에 맞춰 제품은 다음 네 가지를 중심으로 설계한다.

### 1. 불변성

과거 요청이나 결정 기록이 이후 수정되면 이를 탐지할 수 있어야 한다.

### 2. 완전성

관측된 요청에 대응하는 결정이 정해진 시간 안에 남지 않았다면 이를 확인할 수 있어야 한다.

### 3. 독립 검증

기관의 현재 서버나 DB가 없어도 제3자가 한 건의 요청과 결정을 검증할 수 있어야 한다.

### 4. 부인 방지

Agent와 기관이 나중에 자신이 보낸 요청이나 내린 결정을 쉽게 부인할 수 없어야 한다.

## 10. 핵심 데모 시나리오

### Demo 1 — 정상 거절 검증

- 기업 한도: $4,000
- Agent 요청: $4,500
- 기관 결정: REJECT

제3자 Verifier는 요청, 정책, 기관 결정, 기록 무결성을 확인하고 정상적인 거절임을 보여준다.

---

### Demo 2 — 결정 기록 수정

기관이 과거의 거절 사유를 다른 내용으로 변경한다.

예:

> 기존: `LIMIT_EXCEEDED`  
> 변경: `KYT_RISK`

Verifier는 현재 기록이 당시 남겨진 증거와 다르다는 사실을 탐지한다.

---

### Demo 3 — 결정 기록 삭제

기관 DB에서 과거 거절 기록을 삭제한다.

우리의 목표는 “DB에서 삭제 버튼을 눌렀다”는 행위 자체를 증명하는 것이 아니다.

대신 기관 DB에 현재 기록이 없더라도 **당시 요청과 결정이 실제로 존재했다는 사실을 독립적으로 다시 확인할 수 있음**을 보여준다.

---

### Demo 4 — 결정 누락

Verification Layer에는 Agent 요청이 존재하지만 기관이 정해진 시간 안에 결정을 남기지 않는다.

- 기한 전 → `PROCESSING`
- 기한 후 → `MISSING`

이를 통해 관측된 요청에 대응하는 결정이 누락됐음을 확인한다.

---

### Demo 5 — Agent의 가짜 주장

Agent가 실제로 Verification Layer를 통과하지 않은 과거 요청을 새로 만들어 기관의 책임이라고 주장한다.

Verifier는 당시 관측된 원 요청 증거가 없다는 사실을 확인하고 검증 불가능한 주장으로 처리한다.

## 11. 기존 Agent Payment 프로토콜과의 차이

기존 Agent Payment 표준도 권한 증명, 승인·거절 Receipt, 분쟁 증거 구조를 다룬다.

따라서 우리는 다음과 같이 주장하지 않는다.

> “기존에는 거절 기록이 존재하지 않는다.”

또는

> “우리가 최초로 거절 영수증을 만든다.”

우리 프로젝트의 초점은 **개별 Receipt를 새로 만드는 것**이 아니다.

차별점은 다음과 같다.

> **Agent의 요청이 들어온 순간부터 기관의 정책 판단과 최종 결정까지를 하나의 외부 검증 가능한 흐름으로 연결하고, 이후 분쟁 시 어느 한쪽의 내부 DB 없이 전체 판단 과정을 제3자가 다시 확인할 수 있게 한다.**

즉 핵심은 `Receipt 생성`보다 **독립적인 Decision Verification**이다.

---

## 12. MVP에서 만들지 않는 것

범위를 명확히 하기 위해 다음 항목은 이번 MVP에서 제외한다.

- 실제 금융기관 Wallet 연동
- 실제 자금 전송
- Agent Payment 전체 프로토콜 구현
- AP2 전체 연동
- 복잡한 정책 엔진
- KYT / AML / AI 위험 판단의 정확성 검증
- 기관 서명키 탈취 대응
- Agent와 기관의 완전한 공모 대응
- 전체 기업 감사 시스템
- 실서비스 수준의 운영 대시보드

필요한 경우 Mock Agent와 Mock Institution Wallet을 사용한다.

MVP의 성공 기준은 **“한 건의 거절이 발생하고 → 검증 가능한 증거가 남고 → 이후 제3자가 기관 DB 없이 이를 확인하는 핵심 경로가 실제로 동작하는가”**이다.

---

## 13. 현재 확정된 제품 방향

현재 팀이 합의한 핵심 방향은 다음과 같다.

- Agent Payment 전체가 아니라 **기관 Wallet의 오프체인 승인·거절 판단**에 집중한다.
- 대표 정책은 **1회 결제 한도 $4,000 USDC** 하나만 사용한다.
- 대표 요청은 **$4,500 USDC**로 고정한다.
- Verification Layer는 **Agent와 Institution 사이의 필수 경로**로 둔다.
- 평상시에는 증거를 남기고, 분쟁 시 제3자가 이를 검증한다.
- 기관 DB를 신뢰하지 않는 **독립 검증**을 가장 중요한 가치로 둔다.
- 수정, 삭제, 결정 누락을 핵심 공격 시나리오로 사용한다.
- 실제 Agent Payment에서 동일한 분쟁이 이미 빈번하다고 과장하지 않는다.
- 현재 시장이 Agent Payment의 권한·분쟁 증거 문제를 사전에 준비하고 있다는 점을 배경으로 삼는다.

---

## 14. 핵심 메시지

> **기관의 로그를 믿는 것이 아니라, 당시 남겨진 증거를 검증한다.**

또는 조금 더 제품 관점으로 표현하면:

> **Agent Payment의 오프체인 판단을, 나중에도 제3자가 확인할 수 있는 증거로 만든다.**
